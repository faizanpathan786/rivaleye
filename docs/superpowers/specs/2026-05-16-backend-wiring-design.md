# Backend Wiring Design — Phase 1 MVP

**Date:** 2026-05-16
**Scope:** API + DB only. Workers are out of scope (pipeline already runs end-to-end).
**Goal:** Wire `@rivaleye/api` to support the Phase 1 frontend MVP: anonymous report creation, polled status, and a Reddit-only PRD §10 output shape.

---

## 0. Locked constraints

- **No auth in MVP.** Reports endpoints are anonymous. `authPlugin` stays in the repo but is not applied to `reportsController`.
- **Reddit only.** No other platform endpoints, no platform selection UI.
- **Workers untouched.** Existing `scrape-platform` + `generate-report` pipeline (worker reads `reports.goal`, `reports.audience`, writes `reports.output`/`reports.status`) is the contract — DB columns must remain readable/writeable in the names workers already use.
- **Founder goal persists on the row** and must be available to the LLM clustering job (already pulled via `db.select().from(reports)` in `worker/src/jobs/generate-report.ts`).
- **Output shape = PRD §10** (10 sections). New fields are added without breaking the existing `PainReportOutput` consumers.

---

## 1. DB schema changes

All changes go through a single Drizzle migration. Schema source: `packages/api/src/db/schema/reports.ts`.

### 1.1 Current state (already on disk)

```
reports (
  id            uuid pk,
  owner_id      uuid null fk users.id,
  category      text not null,
  competitors   jsonb not null,         -- string[]
  audience      text null,
  goal          report_goal not null,   -- enum
  status        report_status not null default 'queued',
  output        jsonb null,
  created_at    timestamp not null,
  updated_at    timestamp not null
)
```

`report_goal` enum already exists with the 6 values requested. `report_status` enum has `queued | running | completed | failed`.

### 1.2 Changes

| Change | Column | Type | Notes |
|---|---|---|---|
| ADD | `stage` | `report_stage` enum | New enum: `queued | scraping | clustering | done | failed`. Drives frontend polling UI. Defaults `'queued'`. Nullable: **no**. |
| ADD | `error` | `text` | Nullable. Set when `stage = 'failed'`. Short human-readable string; full stack stays in worker logs. |
| KEEP | `goal` | `report_goal` | No change. Already matches user spec values (`decide_mvp_features` instead of `decide_mvp`, `find_user_pain` instead of `find_pain` — see §1.3). |
| KEEP | `audience` | `text` | Already exists. Treated as `target_audience` in API/shared schemas. |
| KEEP | `output` | `jsonb` | Type widened (TS-level only) to `ReportOutput` (§1.4). Existing `PainReportOutput` rows remain readable — new fields are optional in the Zod schema during the MVP backfill window. |
| KEEP | `status` | `report_status` | Retained for backwards compatibility with the worker (`generate-report.ts` writes `status: 'completed' | 'failed'`). New `stage` column is the canonical state for the frontend. See §1.5. |

No `report_sources` table. Source evidence lives inline in `output.sources[]` (see §1.4). Decision rationale: MVP volume is small, sources are read together with the report, and a separate table would force a join + extra DTO assembly for no benefit.

### 1.3 Founder goal enum — naming reconciliation

User spec lists `decide_mvp` and `find_pain`. The existing enum uses `decide_mvp_features` and `find_user_pain`. **Keep the existing enum values** — they are already migrated and referenced by the worker. The frontend Zod re-export uses the same names. No migration needed for the enum.

If the product copy must show shorter labels, do that mapping in the web layer, not the DB.

### 1.4 `output` jsonb shape (PRD §10)

```ts
type ReportOutput = {
  executive_summary: string;
  top_opportunities: [Opportunity, Opportunity, Opportunity]; // exactly 3
  strongest_positioning_angle: string;
  best_wedge: string;
  pain_clusters: PainCluster[];
  feature_gaps: FeatureGap[];
  pricing_pain: string;
  switching_signals: SwitchingSignal[];
  voice_of_customer: string;          // PRD §10: single narrative paragraph
  competitor_weaknesses: string[];
  product_opportunities: string[];
  positioning_angles: string[];
  next_actions: string[];
  sources: Source[];
};

type Opportunity = {
  title: string;          // 3-7 words
  rationale: string;      // 1-2 sentences
  evidence_ids: string[]; // foreign refs into sources[].id
};

type PainCluster = {
  id: string;
  title: string;
  description: string;
  severity: "high" | "medium" | "low";
  mention_count: number;
  evidence_ids: string[];
};

type FeatureGap = {
  title: string;
  description: string;
  evidence_ids: string[];
};

type SwitchingSignal = {
  quote: string;
  context: string;        // e.g. "user moved from X to Y"
  evidence_ids: string[];
};

type Source = {
  id: string;             // short uid generated by worker (e.g. "s_1a2b")
  platform: "reddit";
  url: string;
  title: string | null;
  excerpt: string;        // <= 400 chars
  author: string | null;
  score: number | null;
  posted_at: string | null; // ISO
};
```

Naming convention: snake_case keys inside `output` (it is a wire shape, not TS code). The Zod schema mirrors this; TS types are generated via `z.infer`.

### 1.5 `stage` vs `status` — transition plan

For MVP both columns are written by the worker. Mapping:

| stage | status (legacy) |
|---|---|
| `queued` | `queued` |
| `scraping` | `running` |
| `clustering` | `running` |
| `done` | `completed` |
| `failed` | `failed` |

The frontend reads **`stage` only**. After Phase 1 lands and the worker is updated to write `stage` directly, `status` is dropped in a follow-up migration. For MVP, `status` keeps its `notNull` + default and is set by the worker as it does today; the API write path also sets `stage` on creation.

### 1.6 Migration mechanics

1. Edit `packages/api/src/db/schema/reports.ts`:
   - Add `reportStageEnum` pgEnum.
   - Add `stage` column with `.notNull().default("queued")`.
   - Add `error: text("error")`.
2. Run `pnpm db:generate` from repo root — emits `packages/api/drizzle/000X_<name>.sql`.
3. Inspect generated SQL: it should be `CREATE TYPE report_stage AS ENUM (...)`, `ALTER TABLE reports ADD COLUMN stage ...`, `ALTER TABLE reports ADD COLUMN error ...`. Reject and re-generate if Drizzle proposes anything else.
4. Run `pnpm db:migrate`.
5. **Backfill:** all existing rows get `stage = 'queued'` from the default. No data-migration script needed — existing rows are dev-only and will be re-run.

Commit the schema edit and the generated SQL in the same commit, per `packages/api/CLAUDE.md` §12.7.

## 2. API endpoints

All endpoints under `/v1/reports`, mounted in `packages/api/src/controllers/reports/index.ts`. **No auth applied.**

### 2.1 `POST /v1/reports`

**Body (Elysia `t.*`):**

```ts
t.Object({
  category: t.String({ minLength: 1 }),
  competitors: t.Array(t.String({ minLength: 1 }), { minItems: 1, maxItems: 5 }),
  target_audience: t.String({ minLength: 1 }),    // required in MVP
  founder_goal: t.Union([
    t.Literal("validate_idea"),
    t.Literal("find_weaknesses"),
    t.Literal("improve_positioning"),
    t.Literal("decide_mvp_features"),
    t.Literal("find_user_pain"),
    t.Literal("compare_alternatives"),
  ]),
})
```

**Behavior:**

1. Validate body (Elysia).
2. Call `reportsService.createReport(input)`:
   - Insert row: `category`, `competitors`, `audience = target_audience`, `goal = founder_goal`, `stage = 'queued'`, `status = 'queued'`, `owner_id = null`.
   - Return new `id`.
3. Enqueue worker: `enqueueScrapePlatform({ reportId, platform: 'reddit', competitor: competitors[0], category })`. For MVP only the first competitor is processed; multi-competitor fan-out is a Phase 2 concern.
4. Respond `201` with `{ id, stage: 'queued' }`.

**Notes:**

- The current `create-report.ts` calls `runReport(...)` directly (API-side). That path is **removed** in this spec — the API must only enqueue (per root `CLAUDE.md` rule 10). `runReport` and its `report-generator.ts` are deleted from `packages/api/src/services/` (the worker has its own `generate-report.ts`).
- `platforms` is removed from the request body. The worker is hardcoded to Reddit for MVP.
- No `goal` default. The field is required.

**Response shape:**

```ts
t.Object({ id: t.String(), stage: t.Literal("queued") })
```

### 2.2 `GET /v1/reports/:id`

**Params:** `{ id: string }` (uuid).

**Behavior:**

1. `reportsService.getReport(id)` → single row or `null`.
2. If `null`, return `404 { message: "report not found" }`.
3. Else return the row mapped to wire shape (§2.4).

**Response:**

```ts
{
  id: string;
  category: string;
  competitors: string[];
  target_audience: string | null;
  founder_goal: ReportGoal;
  stage: ReportStage;
  error: string | null;
  output: ReportOutput | null;     // null until stage === 'done'
  created_at: string;              // ISO
  updated_at: string;              // ISO
}
```

`audience` → `target_audience` and `goal` → `founder_goal` renames happen in the controller mapper, not the DB.

### 2.3 Skipped endpoints

- `GET /v1/reports` (list) — not implemented. The frontend tracks anon history in localStorage.
- `DELETE /v1/reports/:id` — not implemented for MVP.
- The current `list-reports.ts` handler is removed from `reportsController` (file may be left on disk or deleted; preference: delete to avoid dead code).

### 2.4 Controller / service split

Per `packages/api/CLAUDE.md` §3 and §5:

- `controllers/reports/handlers/create-report.ts` — Elysia handler, t.* schema, calls service, shapes response.
- `controllers/reports/handlers/get-report.ts` — Elysia handler, calls service, maps row → wire shape, handles 404.
- `services/reports.service.ts` — new file. Exports:
  - `createReport(input: CreateReportInput): Promise<{ id: string }>` — inserts row + enqueues.
  - `getReport(id: string): Promise<Report | null>` — single-row select.
- `services/report-generator.ts` — **deleted** (logic lives in worker).

The service is the only place that touches `db` for reports. Handlers never call `db.*` directly.

## 3. `@rivaleye/shared` schemas

Edit `packages/shared/src/schemas/report.ts` and `packages/shared/src/types/index.ts`.

### 3.1 Additions

- `reportStageSchema = z.enum(["queued", "scraping", "clustering", "done", "failed"])`.
- `sourceSchema`, `painClusterSchema`, `featureGapSchema`, `switchingSignalSchema`, `opportunitySchema` — Zod equivalents of §1.4.
- `reportOutputSchema` — Zod object matching `ReportOutput` exactly. `top_opportunities` uses `z.tuple([...]).rest(...)` capped at 3 (or `z.array().length(3)` — pick `.length(3)` for simpler errors).
- `createReportInputSchema` — replaced to match the new POST body (`target_audience` required, `platforms` dropped, `founder_goal` required).
- `reportDtoSchema` — Zod for the GET response shape (§2.2).

### 3.2 Compatibility

- The existing `PainReportOutput` type stays exported as a deprecated alias to `ReportOutput` until the worker is updated to emit the new shape. Worker updates are out of scope for this spec, but the shared schema must accept **both** shapes during the transition:
  - Approach: `reportOutputSchema` is the new strict shape. Add `legacyReportOutputSchema` for the existing `PainReportOutput`. Frontend reads `output` as `ReportOutput | LegacyReportOutput | null` and handles the legacy variant with a thin adapter. **Once the worker emits §1.4, drop the legacy schema in a follow-up.**
- Re-export everything from `packages/shared/src/index.ts`.

### 3.3 FounderGoal enum

The existing `reportGoalSchema` already lists the 6 values the user named (modulo `decide_mvp_features` / `find_user_pain` — see §1.3). No change.

## 4. Auth bypass strategy

`packages/api/src/plugins/auth.ts` currently exports `authPlugin` with a macro that 401s when there is no user. Reports controller has never wired it (see `create-report.ts`, `get-report.ts` — no `.use(authPlugin)`).

**Plan:**

1. Do **not** delete `authPlugin` or `packages/api/src/plugins/auth.ts`.
2. Do **not** apply `authPlugin` to `reportsController` or its handlers.
3. Add a top-of-file comment in `controllers/reports/index.ts`:

   ```
   // MVP: anonymous report creation. authPlugin intentionally not applied.
   // Re-introduce per packages/api/CLAUDE.md §12.9 when user accounts ship.
   ```

4. The root `CLAUDE.md` rule "Permission-first" (§9) is suspended for this controller during MVP. Note this exception in the project TODO list at the bottom of `packages/api/CLAUDE.md` so it is not forgotten.
5. `owner_id` stays nullable in the schema. All MVP rows insert `owner_id = null`.

This is **temporary**. The first auth-enabled feature (likely "save report to my account") re-applies `authPlugin` to `POST /reports` with `auth: { permissions: [PERMISSIONS.REPORTS_CREATE] }` and populates `owner_id` from `user.id`.

## 5. Migration & rollout plan

1. **Schema** — edit `reports.ts`, `pnpm db:generate`, inspect SQL, `pnpm db:migrate`. Single migration file.
2. **Shared** — update Zod schemas + types, bump nothing (workspace `*`).
3. **API**
   - Delete `packages/api/src/services/report-generator.ts`.
   - Delete `packages/api/src/controllers/reports/handlers/list-reports.ts` and remove its mount in `reports/index.ts`.
   - Create `packages/api/src/services/reports.service.ts`.
   - Rewrite `create-report.ts` to: validate, call service, enqueue, respond.
   - Rewrite `get-report.ts` to: call service, map to DTO, 404 on miss.
4. **Verification (manual)**:
   - `pnpm --filter @rivaleye/api dev` boots clean on `:6090`.
   - `POST /v1/reports` with a valid body returns `{ id, stage: "queued" }`.
   - `GET /v1/reports/:id` returns the row with `stage` advancing as the worker progresses.
   - Worker (untouched in this spec) still picks up the enqueued job from `scrape-platform`.
5. **Commit**: schema change + generated migration + service/controller edits + shared schema edits, all in one PR.

---

## 6. Out of scope

- Rate limiting / abuse protection.
- User accounts, sessions, better-auth wiring.
- Billing / Stripe.
- Multi-platform scraping endpoints, platform-specific routes.
- Comparison endpoints (multi-report diffs).
- Webhooks / push notifications to the frontend.
- Updating the worker to emit the new §1.4 output shape (tracked separately).
- Dropping the legacy `status` column (Phase 2 follow-up).
- Source persistence in a separate table (`report_sources`) — explicitly rejected for MVP in §1.

---

## 7. Open questions (non-blocking)

- Should `target_audience` be optional? Spec marks it required because the LLM prompt benefits from it; if onboarding friction shows up, relax to `z.string().optional()` and the worker falls back to a generic audience.
- `top_opportunities` length: PRD says "3"; the schema enforces exactly 3. If the LLM occasionally returns 2, the worker should pad with a sentinel rather than the API rejecting the write. This is a worker concern, noted here for traceability.
